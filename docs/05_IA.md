# Analyse par intelligence artificielle

Le principe directeur : **le modèle propose, les contrôles déterministes
disposent**. Aucune valeur produite par l'IA n'est écrite sans avoir
traversé une vérification arithmétique.

---

## Traitement asynchrone par lots (`queue_job`)

L'analyse d'un ticket peut prendre de quelques secondes (API cloud) à
plusieurs dizaines de secondes, voire plus d'une minute (modèle local sur
un GPU déjà chargé). Un appel synchronique dans le processus web Odoo se
heurte à `limit_time_real` (~120 s par défaut) : au-delà, Odoo tue le
worker qui exécute la requête — c'est le « plantage » observé avec les
modèles locaux. L'analyse est donc **toujours** déléguée à `queue_job`
(OCA), jamais exécutée dans la requête qui l'a déclenchée, y compris pour
le bouton **Analyser avec l'IA**.

### Un seul canal, capacité 1 : exclusivité du GPU

```
root.js_depenses            capacité = 1   (verrou global)
├── root.js_depenses.vision
└── root.js_depenses.text
```

Le canal parent a une capacité de **1** : comme les jobs des deux
sous-canaux en dépendent, un seul job — vision ou texte, peu importe —
s'exécute à la fois, quel que soit le nombre de workers Odoo disponibles.
C'est délibéré : avec un unique GPU/instance Ollama (20 Go), exécuter un
appel vision et un appel texte « en parallèle » du point de vue de
`queue_job` reviendrait, côté GPU, à charger et décharger un modèle en
boucle — Ollama ne garde chargé que le dernier modèle sollicité. Cette
exclusivité coûte rien sur un moteur cloud (où la notion de « modèle
chargé » n'existe pas) et évite tout thrashing sur un moteur local.

### Traitement par lots, phase par phase

Un lot de tickets (taille configurable, réglage société **Taille des
lots d'analyse**, 10 par défaut) est traité entièrement en vision, puis
entièrement en texte, plutôt que ticket par ticket de bout en bout :

```
Lot de N tickets prêts (état "Analyse IA")
        |
        v
┌─────────────────────────────────────────────────────────┐
│ Job vision (canal .vision) — un seul modèle chargé        │
│   pour tout le lot                                        │
│                                                             │
│   pour chaque ticket :                                    │
│     Prétraitement image (EXIF, réduction, contraste)      │
│     OCR Tesseract (transcription déterministe)             │
│     Modèle de vision → lecture libre du ticket             │
│       (PAS de schéma JSON imposé à cette étape)            │
│     → ai_vision_text                                       │
└──────────────────────────┬──────────────────────────────┘
                            |
                            v
┌─────────────────────────────────────────────────────────┐
│ Job texte (canal .text) — le modèle vision est déchargé,   │
│   le modèle texte chargé une seule fois pour tout le lot   │
│                                                             │
│   pour chaque ticket :                                    │
│     Modèle texte → structuration JSON à partir de          │
│       ai_vision_text (schéma imposé, boucle de correction  │
│       arithmétique)                                        │
│     Analyse Decimal, Σ lignes = total ?                    │
│     Affectation comptable (règles apprises, puis IA)        │
└─────────────────────────────────────────────────────────┘
```

Chaque ticket est traité indépendamment à l'intérieur du lot (une
exception sur l'un n'arrête pas les autres, à l'image de l'ancienne tâche
planifiée) ; le lot suivant n'est enfilé sur `.vision` que lorsque le
précédent est complet.

### Pourquoi deux moteurs plutôt qu'un seul appel

`qwen3-vl` (et les modèles de vision locaux en général) lisent
correctement une image mais suivent mal un schéma JSON strict quand les
deux exigences sont combinées dans le même appel. Séparer les deux
métiers — **lire** (vision, texte libre) puis **structurer** (texte
seul, schéma JSON strict) — donne de bien meilleurs résultats, et permet
de ne relancer que l'étape de structuration en cas d'écart arithmétique,
sans reconsommer d'image ni de calcul de vision.

### Option « le modèle vision fait aussi le JSON » (`json_from_vision`)

Certains moteurs — typiquement les API cloud (GPT-4o, Claude, Pixtral) —
suivent un schéma JSON strict même en présence d'une image. Pour ces
moteurs, cocher **`json_from_vision`** sur la fiche du moteur (`js.ai.provider`)
supprime l'étape texte séparée : le job vision produit directement le
JSON structuré (schéma imposé, boucle de correction arithmétique incluse)
et le ticket passe directement à *À vérifier* dès ce job — pas de job
texte du tout pour ces tickets-là. Décoché par défaut ; à réserver aux
moteurs dont la fiabilité JSON en mode vision a été vérifiée. Les moteurs
préconfigurés cloud (OpenAI, Anthropic, Mistral) l'activent par défaut ;
Ollama local ne l'active pas.

### Traçabilité

Le champ `ai_vision_text` conserve la transcription libre produite par
le modèle de vision (visible sur l'onglet **Analyse IA** du ticket), utile
pour diagnostiquer un échec de structuration sans avoir à rejouer l'appel
vision. L'échange correspondant est journalisé dans `js.ai.log` avec
l'étape `vision`.

### Retraitement après échec

Le job qui échoue sur un ticket (erreur réseau, moteur indisponible,
JSON toujours incohérent après relances) consigne l'erreur sur le
ticket, ne bloque pas le reste du lot, et remet le ticket en `draft` avec
`needs_ai_analysis = True` tant que le nombre d'essais (3 par défaut)
n'est pas atteint : la tâche planifiée le reprendra dans un lot suivant.
Au-delà, l'analyse est abandonnée et le bouton **Relancer l'analyse**
permet de repartir à zéro. `queue_job` propose par ailleurs son propre
mécanisme de relance technique (`retry_pattern`, configuré sur les deux
canaux) en filet de sécurité pour un job qui échouerait franchement
(bug, perte de connexion base de données), indépendamment de cette
logique métier.

## Chaîne d'extraction d'un ticket

```
Pièces jointes (photo, PDF)
        |
        v
  Prétraitement image        redressement EXIF, réduction, contraste
        |
        v
  OCR Tesseract              transcription déterministe des caractères
        |
        v
  Modèle vision              lecture libre (image + texte OCR)
        |
        v
  Modèle texte               structure le JSON à partir de cette lecture
        |                    (ou : modèle vision directement, si
        |                     json_from_vision est activé)
        v
  Analyse Decimal            conversion rigoureuse des montants
        |
        v
  Contrôle arithmétique      Σ lignes = total ?
        |
   ┌────┴─────┐
   │ non      │ oui
   v          v
Relance    Affectation comptable
ciblée     (règles apprises, puis IA sur liste restreinte)
```

Cette chaîne est exécutée par les jobs `queue_job` décrits ci-dessus
(chaque job n'en parcourt qu'une partie), mais reste aussi disponible en
un seul appel synchrone via `js.ticket.extractor.analyze()`, utilisé par
les tests et pour un usage direct hors file d'attente.

---

## Pourquoi l'OCR en plus du modèle

Un modèle de vision « lit » une image de façon probabiliste : il peut
produire `12.90` là où figure `12.99`. Tesseract, lui, transcrit les
caractères de manière déterministe et reproductible.

Le modèle reçoit donc **les deux** : l'image pour la structure (quelles
lignes, quel ordre, quels regroupements) et la transcription OCR comme
source de référence pour les chiffres. La consigne le lui indique
explicitement.

L'OCR est facultatif : en son absence, la chaîne fonctionne en mode
vision seule, avec une fiabilité moindre sur les montants.

---

## Consigne donnée au modèle

Extrait du prompt système de lecture (`VISION_SYSTEM_PROMPT`, étape
vision) et de structuration (`SYSTEM_PROMPT`, étape texte — les deux
partagent les mêmes règles de fond) :

> - Tu ne transcris que ce qui est réellement imprimé. Tu n'inventes aucun
>   montant et tu ne complètes aucune valeur absente.
> - Les montants sont recopiés tels quels, avec deux décimales, sans
>   symbole monétaire.
> - En Suisse, les montants affichés sur un ticket sont presque toujours TTC.
> - Le séparateur de milliers peut être une apostrophe : 1'234.50 vaut 1234.50.
> - Si une information est illisible, tu renvoies une chaîne vide.

L'étape vision répond en texte libre (aucun schéma imposé : c'est
justement ce qui la rend fiable avec une image). L'étape texte répond
avec les montants demandés **sous forme de chaînes**, jamais de nombres :
un modèle produit trop souvent un JSON numérique mal formé, alors qu'une
chaîne peut être analysée rigoureusement côté Python.

Le schéma de réponse de l'étape texte est imposé aux moteurs qui le
supportent (`format` chez Ollama, `response_format` chez OpenAI).

---

## Boucle de correction arithmétique

C'est le mécanisme qui distingue une extraction exploitable d'une
hallucination. Un modèle qui invente un montant produit presque toujours
une somme incohérente.

```python
gap = Σ(montants des lignes) − total annoncé
```

Si l'écart n'est pas nul, le modèle est relancé — non par une simple
répétition, mais avec **l'écart constaté** :

> La somme des lignes que tu as extraites vaut 43.20 alors que le total
> du ticket est 45.60, soit un écart de -2.40. Relis attentivement le
> ticket : une ligne est probablement manquante, en trop, ou mal
> recopiée.

Cette formulation conduit le modèle à relire la zone fautive plutôt qu'à
reproduire son erreur. Le nombre de relances est paramétrable (2 par
défaut). Cette relance ne concerne que l'étape texte (rejouer uniquement
la structuration, sans image ni nouvel appel vision) — sauf en mode
`json_from_vision`, où elle rejoue l'appel vision complet puisque c'est
lui qui produit le JSON.

Si l'écart persiste, les données sont **tout de même reportées** sur le
ticket, mais l'état reste « À vérifier », la confiance est abaissée à
0.40, un message est publié dans le fil de discussion et le bandeau rouge
s'affiche. Rien n'est masqué à l'utilisateur.

## Affectation comptable en deux temps

**1. Règles apprises d'abord.** Les libellés déjà connus n'ont pas besoin
d'être soumis au modèle : c'est plus rapide, plus fiable et gratuit.

**2. Liste restreinte pour le reste.** Seules les lignes non résolues
partent vers l'IA, accompagnées d'une sélection d'une quarantaine de
comptes plausibles — jamais les 126 du plan comptable, ce qui dégraderait
la réponse et allongerait le traitement.

La liste est constituée par `_build_account_shortlist()` :

1. comptes déjà employés avec ce fournisseur sur des tickets antérieurs
   validés — le signal le plus fort ;
2. comptes déjà employés avec ce fournisseur en comptabilité
   (`account.move.line`) ;
3. comptes dont l'intitulé recoupe les mots du libellé ;
4. complément par les comptes de charge les plus courants.

Le modèle répond par un objet de correspondances
`{"libellé": "code"}`, et **seuls les codes figurant dans la liste sont
acceptés** : une invention de code est ignorée. Cet appel se fait sur le
modèle texte, dans le même job que la structuration.

Le choix final alimente à son tour les règles apprises.

---

## Choix de la taxe

Le taux lu sur le ticket prime sur la taxe par défaut du compte, car un
même compte peut recevoir plusieurs taux.

`_resolve_taxes()` procède ainsi :

1. une taxe du compte correspond exactement au taux lu → retenue ;
2. sinon, recherche parmi les taxes d'achat de la société d'une taxe de
   ce taux **conservant le mode d'inclusion** de la taxe du compte, afin
   de ne jamais basculer involontairement de TTC à HT ;
3. à défaut, la taxe par défaut du compte s'applique.

## Moteurs configurables

Quatre types sont pris en charge : `ollama`, `openai`, `anthropic`,
`mistral` / compatible OpenAI. Plusieurs moteurs peuvent coexister, ce
qui permet de **comparer leur fiabilité sur vos tickets réels** avant
d'arbitrer entre local et distant.

| Réglage | Rôle |
|---|---|
| `base_url` | Adresse du service |
| `api_key_value` | Champ de saisie de la clé. Elle est aussitôt rangée dans les paramètres système et jamais conservée sur la fiche |
| `api_key_param` | Détail technique déterminé automatiquement, masqué hors mode développeur |
| `model_vision` | Modèle de lecture d'image |
| `model_text` | Modèle de structuration JSON et d'affectation comptable |
| `json_from_vision` | Le modèle vision produit directement le JSON structuré ; l'étape texte séparée est sautée |
| `temperature` | 0.00 par défaut, pour la reproductibilité |
| `timeout`, `max_retries` | Robustesse réseau |

Les clés d'API ne sont **jamais stockées** dans la fiche du moteur, mais
dans les paramètres système, référencées par leur nom.

Moteurs préconfigurés : Ollama local (actif par défaut, `json_from_vision`
décoché), Ollama modèles cloud, OpenAI, Anthropic, Mistral (inactifs, à
compléter — `json_from_vision` coché pour ces trois derniers).

### Particularités d'Anthropic

Deux points spécifiques à ce fournisseur, découverts à l'usage :

- **`temperature` est refusé par les modèles récents** (Claude Sonnet 5,
  Opus 5, Fable 5...), qui recourent à un raisonnement adaptatif permanent.
  L'API répond alors par une erreur HTTP 400
  (`` `temperature` is deprecated for this model ``). Plutôt que de
  maintenir une liste de modèles à jour, `_ask_anthropic()` tente d'abord
  la requête avec `temperature`, puis la rejoue automatiquement sans ce
  paramètre si l'API le signale obsolète. Les modèles plus anciens
  (Haiku 4.5) qui l'acceptent encore ne sont pas pénalisés.
- **Pas de schéma JSON imposable** : contrairement à OpenAI
  (`response_format`), l'API Messages d'Anthropic n'offre pas de mécanisme
  de contrainte stricte du format de sortie. Le champ « Sortie
  structurée » est donc masqué pour ce fournisseur — il n'aurait aucun
  effet — et la fiabilité du JSON repose entièrement sur la consigne du
  prompt (`SYSTEM_PROMPT`).

## Traçabilité

Chaque échange est consigné dans `js.ai.log` : consigne, requête,
réponse, durée, nombre d'images, succès ou message d'erreur, numéro
d'itération, étape (`vision`, `extract`, `fix`, `accounts`, `other`).
Cela permet de comprendre a posteriori pourquoi une extraction a échoué,
et de comparer objectivement les moteurs.

Le bouton **Tester la connexion** vérifie qu'un moteur répond sans
consommer d'image.

---

## Limite à garder à l'esprit

L'IA ne comptabilise jamais. Elle pré-remplit un ticket qu'un humain
vérifie et valide. Les garde-fous arithmétiques ne rendent pas
l'extraction exacte : ils garantissent qu'une incohérence est **détectée
et affichée** plutôt que silencieusement comptabilisée.

Sur des tickets thermiques décolorés ou froissés, aucun moteur actuel
n'atteint une fiabilité permettant de se passer de relecture.
